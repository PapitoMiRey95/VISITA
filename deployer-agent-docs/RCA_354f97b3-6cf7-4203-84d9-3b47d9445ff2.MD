## Headline root cause
1. **`patient_directory` (the canonical record shown in the Patients view) has NO `health_card_issue_date` and NO `health_card_expiry_date` keys on ANY of the 51 ACTIVE linked records.** The schema simply does not carry those two fields. So HC Issue/Expiry can never render for a portal-linked patient regardless of what the registration form captured. **This is the dominant cause of the reported "missing HC Issue/Expiry".**
2. **Sex**: directory stores `sex_code` (numeric "1"/"2") on 49/51 and a human `sex` string on only **4/51**. The registration `patients` doc stores `sex` as a string. If the Patients view reads a `sex` string off the directory doc, it shows blank for ~47 even though the canonical `sex_code` exists.
3. **HC Version Code**: directory DOES hold `health_card_version_code` on 50/51 (only PIN 4075 blank). The registration doc uses a *different* field name `health_card_version`. So a missing "Version Code" in the UI is most likely a field-name mapping issue, not absent data — plus several version values disagree between the two collections (see §3).

These are **field-name / schema-mapping (Code) issues**, not data loss. For the dates specifically, the original values still exist in the registration `patients` doc for 40 of 51 and are recoverable.

## 3. Name mismatch (reg first+middle+last+second_last vs dir first+last, alnum-lowercased)
**≈22 of 51 differ** (≈20 if accents are ASCII-folded; 2 of the 22 differ only by accent — PIN 509 Agustín/Agustin, 1951 González/Gonzalez). Cause: the directory folds the full given name into `first_name` (e.g. "Angie Sophia", "Leonardo Martin") and the full surname into `last_name` (e.g. "GUARDO HERNANDEZ", "VEGA ESPINOZA DE VARGAS"), while registration split/partial names often omit those extra tokens. Examples differing: 2216, 1886, 433, 491, 1046, 1868, 1247, 2265, 137 (Gutiérrez vs "Guitierrez" misspelling in directory), 796, 2108, 1916, 1068, 2297, 1972, 1056, 1859, 1975, 1560, 1609 (reg duplicates surname in second_last). Also value-level HC discrepancies spotted: PIN 1056 HCN reg `3103459460` vs dir `3103469460`; version-code disagreements reg-vs-dir on PIN 481 (WG/WM), 167 (CA/BD), 1380 (YC/GC), 1511 (HK/JN), 433 (WK/YW).

## 4. Alias / field-name findings (for the display bug)
- **patients** doc uses: `sex` (string), `health_card_version`, `health_card_issue_date`, `health_card_expiry_date`, `matched_directory_id` AND alias **`canonical_directory_id`**, `visita_patient_id`, `directory_match`, `review_queue`, `identity_linked*`, `verification_status`, `portal_status`, `patient_type`, `is_demo`.
- **patient_directory** doc uses: `sex_code` (+ sometimes `sex`), `health_card_version_code` (NOT `health_card_version`), **no `health_card_issue_date`/`health_card_expiry_date` keys at all**, `id`, `visita_patient_id`, `linked_patient_id`, `patient_status`, `norm_first/norm_last/norm_dob/norm_hcn`, `identity_history`, `import_source`, `imported_at`.
- No legacy aliases like `hc_number`, `ohip`, `gender`, `version` were observed. The HCN-with-version concatenation (e.g. `1766164246GC`, `3636491882WK`, `8110739664GK`, `4347298509XY`, `5993-967-941-XN`) is a data-entry pattern in some registration docs, not an alias.

## Suggested fixes (no writes performed by this audit)
- **Code (E1):** The Patients view / directory sync maps the wrong field names. (a) `patient_directory` has no issue/expiry columns — add them and populate from the registration `patients` doc at link time. (b) Decide the Sex source: render from `sex_code` (present 49/51) or sync `sex` string into the directory. (c) Version Code UI should read `health_card_version_code` (directory) consistently; reconcile the reg `health_card_version` vs dir `health_card_version_code` mismatches. (d) Handle HCN+version concatenation in older registration docs.
- **Data (change_mongo_data, user/DB-manager — NOT done here):** 40/51 issue dates and 40/51 expiry dates are recoverable from the registration `patients` docs; ~33 sex values recoverable. 11 issue/expiry and 14 sex values are blank in both and cannot be recovered from the DB (pre-form-field registrations).
