# RCA — visita-admin redeploy failed at `deploy` (deploy_k8s)

## Status
- **Build/deploy status:** FAILED (step `deploy`; `health_check` never ran — "not run: an earlier deploy step failed").
- **New run id:** `ec515b16-9062-4869-858a-4ae632e64b23` (type=redeploy, arch=arm64, tier_0).
- **Live URL:** https://visita-admin.emergent.host — still serving the OLD release (active run `1c8e6185`, image `825b53cd`, amd64). Rollback point intact. The 404 on `POST /api/internal/admin/synthetic-test-patients` is expected: the new code never went live.
- Previous attempt `1fa89fe4` failed with the identical signature.

## Symptom
New pods never became Ready. K8s startup probe on `GET :8080/health` returned 503 repeatedly, then `connection refused` once the backend process exited. Deployment timed out after 10 min (`timeout waiting for deployment to be ready`). Pod events: `Startup probe failed: HTTP probe failed with statuscode: 503` (×56 / ×48 across the two replicas), then `Killing ... failed startup probe`.

## Root cause (code — NOT covered by the applied fix)
The FastAPI startup lifecycle crashes on a **blocking, unprotected MongoDB `createIndexes` call**. Backend stdout tail, verbatim:

```
Starting FastAPI backend: uvicorn server:app --host 0.0.0.0 --port 8001 --workers 1  in /app/backend
INFO:     Started server process [25]
INFO:     Waiting for application startup.
...
pymongo.errors.NetworkTimeout: customer-apps-shard-00-02.zbnnya.mongodb.net:27017: The read operation timed out (configured timeouts: socketTimeoutMS: 60000.0ms, connectTimeoutMS: 10000.0ms)
  File ".../pymongo/collection.py", line 2009, in __create_indexes
  File ".../concurrent/futures/thread.py", line 58, in run
    await db.audit_logs.create_index(keys)
  File "/app/backend/audit_view.py", line 17, in ensure_indexes
    await audit_mod.ensure_indexes(db)
  File "/app/backend/server.py", line 9753, in startup
    await handler()
  File ".../starlette/routing.py", line 732, in lifespan
ERROR:    Application startup failed. Exiting.
Backend died, shutting down nginx...
```

Sequence: uvicorn boots → "Waiting for application startup" → the startup handler at `server.py:9753` calls `audit_view.ensure_indexes` (line 17) → `audit_mod.ensure_indexes(db)` → `db.audit_logs.create_index(keys)`. The TCP/TLS connection to Atlas is established (connectTimeoutMS=10s passed; the SSL socket is mid-`recv_into`), but the `createIndexes` command response does not arrive within socketTimeoutMS=60s → `NetworkTimeout` is raised **uncaught** → FastAPI aborts startup and the process exits → nginx loses its upstream → probes 503/refused → rollout never becomes ready.

**Why the applied fix did not help:** the RCA fix wrapped `storage.init_storage()` in `asyncio.wait_for(asyncio.to_thread(...), timeout=8)` and widened the Mongo client timeouts (serverSelectionTimeoutMS/connectTimeoutMS=10s, socketTimeoutMS=60s). But the crash is on a *different* startup path — `audit_view.ensure_indexes` → `audit_logs.create_index` — which is still called synchronously/unguarded during startup. Raising socketTimeoutMS to 60s actually lets this call block for a full 60s before failing, well inside the readiness window, guaranteeing the crash.

## Suggested fix (E1 / code)
Make index creation non-fatal and non-blocking for app startup, mirroring the storage fix. In `backend/audit_view.py` / the `audit_mod.ensure_indexes` path (and any other `create_index` in the startup handler at `server.py:9753`):
- Wrap `ensure_indexes` in `try/except` catching `pymongo.errors.PyMongoError` (incl. `NetworkTimeout`) so a slow/failed index build logs a warning but does NOT abort startup; create indexes lazily / in a background task after the app is serving, OR
- Call `create_index(..., background=True)` with a short, bounded `asyncio.wait_for` timeout and swallow timeout, letting `/health` come up first.

Secondary: confirm whether the `audit_logs` `createIndexes` is genuinely slow server-side (large collection / index build) versus arm64-cluster → Atlas egress latency. The connection succeeds and the read stalls, which points at a slow index build rather than an IP-allowlist block — but index creation must not gate FastAPI startup regardless.

## Not the cause
- Not a manifest/template issue (build produced a valid image; failure is app startup).
- Not a tier/OOM issue (no OOMKilled/exit 137; pods killed on startup-probe failure).
- Not a missing secret (MONGO_URL resolved; the socket reached Atlas and handshook).
