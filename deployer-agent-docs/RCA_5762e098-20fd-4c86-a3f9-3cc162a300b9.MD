## The remaining blocker (root cause)
The background bootstrap's `audit_indexes` step repeatedly fails against Atlas, so readiness
never flips to 200. Same line every ~75s for the entire readiness window (20:35–20:43):

```
visita - WARNING - [bootstrap] audit_indexes failed: NetworkTimeout:
customer-apps-shard-00-02.zbnnya.mongodb.net:27017: The read operation timed out
(configured timeouts: socketTimeoutMS: 60000.0ms, connectTimeoutMS: 10000.0ms)
```

Interpretation:
- `connectTimeoutMS: 10000` was NOT the failure — TCP reaches Atlas. The **read/operation**
  timed out at the 60s socket deadline, i.e. the `createIndex` command on `audit_logs` never
  completes in time. This is the "Atlas unreachable/slow from the target cluster" scenario.
- Supporting signal: the live/active run (1c8e6185) is **amd64** and talks to Mongo fine (it is
  still serving). All three failed redeploys (1fa89fe4 / ec515b16 / 5762e098) are **arm64** on
  `target-2`. The architecture/cluster path is the differentiator, pointing to an
  infra-level connectivity/performance problem on the arm64 egress path to Atlas (e.g. Atlas
  IP access-list not covering the arm64 cluster egress, or a slow/throttled network path),
  rather than anything in the app image.

## Fix ownership
This is **not** manifest- or source-fixable from here. Two possible paths:
1. **Infra/Platform (primary):** restore Atlas reachability/performance from the arm64
   `target-2` cluster — confirm the cluster's egress IPs are in the Atlas Network Access
   allowlist and that the path to `*.zbnnya.mongodb.net:27017` is not slow/throttled. Until the
   same `createIndex`/ping that the amd64 run completes can complete from arm64, readiness will
   stay 503.
2. **Optional code mitigation (E1, only if infra cannot be changed):** the readiness gate
   currently blocks on full index creation. If Atlas latency from this cluster is inherently
   high, consider making `/health` gate only on a Mongo ping (fail-soft on index creation, same
   as the storage warm-up) so the app can go live while indexes build in the background. This
   is a design change, not a bug fix.

Did NOT loop / re-fire the pipeline — a retry re-hits the identical Atlas timeout.
