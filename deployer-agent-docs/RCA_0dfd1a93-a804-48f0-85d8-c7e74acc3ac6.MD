**Single shared root cause for A, B.conflicts and C.2:** 18 active (+4 closed) `appointment_requests` carry a null/absent `practice_id`. This hides them from practice-scoped views (C.2) and forces the lock backfill to key them under `(null, slot_start)`, which both (a) produces the 4 null-practice HELD-vs-CONFIRMED collisions and (b) prevents collision detection across the practice boundary.

**Required go-live ORDERING (for whoever applies the repair — NOT done here):**
1. Run `stamp_practice_id.py --apply` FIRST — safe (0 conflicts). This removes the null-practice key space.
2. Re-run `backfill_slot_locks.py` (dry-run) AFTER stamping and re-review conflicts — once all records are on dr-aguayo, the 4 collisions become same-practice and must be resolved manually (decide the stale `requested` APT-099/100/103/107 rows: the 3 past ones should be closed; APT-107 vs the confirmed APT-111 on 2026-10-19 11:30 needs a human decision).
3. Then `backfill_slot_locks.py --apply` to create the ~76 missing CONFIRMED/HELD locks.
4. Only then enable verified-patient direct booking. Do NOT backfill before stamping — locks would be created under null practice and the cross-practice collisions would stay hidden.
