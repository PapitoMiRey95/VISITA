## What actually happened (proven)
The backend process starts but **its FastAPI startup never completes**, so uvicorn never binds `:8001`. nginx (same pod) proxies `/health` to `127.0.0.1:8001` and gets **connection refused (111)**; the k8s startup probe 503s for the whole window and kills/restarts the pod, repeatedly → `deploy` times out.

Evidence it is a HANG (blocked), not a crash/exception:
- Backend stdout on every restart ends at `INFO: Waiting for application startup.` and **never** reaches `Application startup complete.` / the app's own `Startup complete` log.
- A filtered log search for `Traceback|Error|Exception|Exiting|startup failed` over the window returned **0 lines** — no exception was raised.
- The container stayed alive ~5 min per cycle (killed by the startup probe), i.e. the uvicorn process was alive-but-blocked the entire time. A startup exception would instead make uvicorn print "Application startup failed. Exiting." and exit immediately (entrypoint.sh then exits 1 and the container restarts in seconds). That is not what happened.

## Why it is NOT the index / seeding work (ruled out)
`@app.on_event("startup")` in `backend/server.py` (~line 9734) runs `create_index`/`ensure_indexes`, then `storage.init_storage()`, then `seed_all`.
- Queried the run's own MongoDB (`visita-admin-test_database`):
  - `audit_logs` count = **1132** (tiny) — the 5 new compound indexes build instantly.
  - `professional_profiles` `linked_user_id` partial-unique index **already exists with the identical spec** → `create_index` is a fast no-op.
  - `visits` `one_active_visit` partial-unique index **already exists with identical spec** → no-op.
- Because the first Mongo op succeeded (indexes present, no 30s ServerSelectionTimeout crash), **MongoDB is reachable from the new pod** and all the index awaits return quickly.
- `seed_all` with `ALLOW_DEMO_SEEDING=false` + `ALLOW_DATA_MIGRATIONS=false` early-returns after a few create-if-missing doc lookups — not a multi-minute blocker. (Both flags are confirmed set; the code also hard-refuses demo seeding / migrations on the live `APP_BASE_URL`.)

So the stall is located AFTER the Mongo ops, at the one synchronous call in the startup coroutine.

## Root cause (inferred, high-confidence)
`backend/storage.py :: init_storage()` is **synchronous** and does a blocking
`requests.post(f"{STORAGE_URL}/init", json={"emergent_key": EMERGENT_KEY}, timeout=30)`
to `INTEGRATION_PROXY_URL` + `/objstore/api/v1/storage`. It is invoked directly inside the **async** `@app.on_event("startup")` handler:
```python
try:
    storage.init_storage()
    logger.info("Storage initialized")
except Exception as e:
    logger.error(f"Storage init failed: {e}")
```
A synchronous `requests` call inside an async startup handler **blocks the entire asyncio event loop**, and uvicorn only opens the listening socket **after** the startup handler returns. If that POST does not return promptly (endpoint unreachable/black-holed from this cluster, or a read-phase stall where the 30s timeout never fires), the startup handler never finishes, `:8001` never binds, and every `/health` probe is refused — exactly the observed signature. The `try/except` does **not** help here: it only catches an exception, not a hang.

Likely trigger for "worked before, fails now": this run moved to a **different target cluster/arch** (failed run is on AWS `deployment-cluster-05`, arm64, ECR image; the live/previous releases ran on GCP, amd64). If reaching the resolved `INTEGRATION_PROXY_URL` object-storage endpoint hangs from the new cluster's network, this latent blocking-call bug surfaces now even though the same code path was fine from the old cluster.

## Recommended fixes
### Code (E1) — primary, required for the new release to deploy
In `backend/server.py` startup, stop letting storage init (or any blocking I/O) gate uvicorn bind. Any ONE of:
1. Remove the eager `storage.init_storage()` from the startup event. It is already lazy — `put_object`/`get_object` call `init_storage()` on first use — so eager init at boot is unnecessary.
2. Or run it off the event loop with a hard deadline:
   `await asyncio.wait_for(asyncio.to_thread(storage.init_storage), timeout=10)` inside try/except (catch `TimeoutError` too).
3. Or make `storage.init_storage` use an async HTTP client (e.g. httpx.AsyncClient) with an explicit total timeout.
Also recommend giving the Mongo client explicit timeouts in `backend/db.py` (`serverSelectionTimeoutMS`, `connectTimeoutMS`, `socketTimeoutMS`) as defense-in-depth so no startup DB op can hang unbounded.

### Platform (parallel check)
Confirm the new target cluster (AWS `deployment-cluster-05`) has egress to the resolved `INTEGRATION_PROXY_URL` object-store `/init` endpoint. If that endpoint is not reachable/slow from this cluster, that is what the blocking call is tripping on. (The code fix above makes the app resilient regardless.)
